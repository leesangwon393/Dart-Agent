## 3. 발견한 버그 (grounded=False 14건 전수 분석 + API 에러 5건)

### 3-A. [수정 완료] Validator 오탐 — 날짜 표기 안의 연도 숫자를 근거없는 숫자로 오탐 (12건)

**증상**: `correction_analysis`(10건: 현대건설/기아/NAVER/신한지주/셀트리온/
와이지엔터테인먼트/두산로보틱스/한화에어로스페이스/이마트/아모레퍼시픽)와
`single_lookup`(2건: 에코프로비엠/HD현대중공업 "최근 공시 이력") 응답에서
`ungrounded_numbers`에 `['2023']`, `['2024']`, `['2025', '2026']` 같은
순수 연도 숫자만 잡혔다.

**원인 확정(기아 사례로 실제 데이터 재현)**: evidence 원문의 보고서명이
`"[기재정정]사업보고서 (2023.12)"`처럼 "YYYY.MM" 형태를 포함하면,
`validator._extract_numbers()`의 정규식(`\d[\d,]*\.?\d*`)이 "2023.12"를
하나의 토큰으로 통째로 추출한다. 그런데 답변이 같은 연도를 "2023년 3월
12일에 제출되었습니다"처럼 점 없이 따로 쓰면, "2023"이 evidence_numbers
집합 안에 별도 항목으로 없어서(그 원문에 "2023"이라는 글자 그대로 존재하는데도)
"근거 없는 숫자"로 오탐됐다.

**실측 재현**: `get_correction_history(company='기아')`를 실제 correction
index로 직접 호출해 얻은 진짜 tool 결과와 배치의 실제 답변 텍스트로
`validate_answer()`를 재실행 → 수정 전 `numbers_grounded=False`,
`ungrounded_numbers={'2023'}` 재현 확인.

**수정**: `src/disclosure_rag/agent/validator.py`의 `_extract_numbers()`에서
"."이 포함된 토큰은 "."로 쪼갠 부분(3자리 이상)도 evidence_numbers 집합에
함께 등록하도록 추가(4줄). 같은 재현 스크립트로 수정 후
`numbers_grounded=True` 확인.

**회귀 테스트**: `tests/test_agent.py::test_validator_does_not_flag_year_
that_is_literal_substring_of_dated_evidence` 추가(get_correction_history
실측 형태를 그대로 재현). 전체 fast suite(`pytest tests/ -m "not slow"`)
97개 전부 통과 확인(기존 실패 0건 유지).

### 3-B. [미수정, 후보로 기록] 알테오젠 calculation — 정확한 뺄셈인데 여전히 ungrounded

"알테오젠의 당기 대비 전기 영업이익 변화" 질문 답변: 당기 41,029,532,343원 /
전기 114,531,644,175원 / 차이 73,502,111,832원. **원문(`periodic_
20260515001517`) 대조 결과 세 숫자 모두 정확**(114531644175-41029532343=
73502111832, 계산도 정확). 그런데도 `ungrounded_numbers=['73502111832']`로
잡혔다.

`_verify_derived_number()`가 evidence 숫자 집합 크기가 `_MAX_VERIFY_
NUMBERS=200`을 넘으면 O(n²) 검산을 통째로 건너뛰고 무조건 "근거없음 의심"으로
처리하는 안전장치가 있다(`validator.py` 20번째 줄). 알테오젠 재무제표 청크처럼
숫자가 밀집된 evidence에서 이 cap에 걸렸을 가능성이 높다(evidence_pack 원문을
따로 저장하지 않아 100% 확정은 못 함). **수정하지 않음** — O(n) 알고리즘으로
바꾸는 리팩터가 필요해 이번 세션 범위를 넘는다고 판단, §5 TODO에 후보로 남김.

### 3-C. [버그 아님, validator가 정확히 잡음] 레인보우로보틱스 — 실제 10배 단위 오류

"레인보우로보틱스의 최근 투자 계획" 답변이 "약 281,784백만 원"이라고 썼는데,
원문(`exchange_20250205900405`)의 실제 투자금액은 **28,178,420,000원
(281.78억원 = 28,178백만원)**이다 — 답변이 정확히 10배 부풀렸다(백만원/억원
단위 변환 실수, 기존에 문서화된 "알테오젠 10배 오류"와 동일 계열의 새로운
사례). 정정본 금액도 동일하게 10배 오류. **validator가 두 숫자 모두 정확히
ungrounded로 잡아낸 것이 맞다** — 오탐이 아니라 validator가 제 역할을 한
사례. 답변 생성 모델의 단위 변환 오류는 여전히 미수정 상태(기존에 알려진
한계, PROJECT_STATE §10 참고).

기존에 "전부 requests 커넥션 에러/타임아웃"으로 뭉뚱그려 있었는데, 정확히는:

실패했다 — 이 템플릿이 유독 hang/실패에 취약한지는 표본이 2건뿐이라 단정할
수 없지만, 다음에 100문항을 다시 돌릴 기회가 있으면 눈여겨볼 가치가 있다.
전부 수십분~97분 hang 후 실패했다는 공통점은 파이프라인 로직 버그라기보다
HCX API 쪽 정체/네트워크 문제로 보는 기존 판단을 유지한다.

코퍼스에 FY2025 보고서가 없었기 때문이다. 그 후 코퍼스가 갱신되며(2026-03
제출 사업보고서들이 새로 들어옴) 데이터는 생겼는데 검색 로직이 못 따라가서,
예전엔 정당했던 "정직한 실패" 응답이 지금은 "실제로는 있는데 못 찾음"으로
바뀐 것으로 보인다 — 코퍼스 성장이 새로운 회귀를 만든 사례.

### 4-E. [기존에 알려졌던, 새로 재확인한] has_citation 판정의 느슨한 폴백

원문대조 중 발견: `validate_answer()`의 `has_citation` 판정에 `"근거" in
answer`라는 매우 느슨한 OR 조건이 있다. 답변 생성 프롬프트가 표준적으로
"근거: report_id(...)"로 끝나도록 유도하기 때문에, **evidence_pack에 실제
증거가 하나라도 있으면(has_any_evidence) 답변에 "근거"라는 글자만 들어가도
citation=True로 통과한다** — report_id가 실제로 맞는지, 진짜 그 근거를
가리키는지는 검사하지 않는다. citation=False 7건이 전부 "근거:" 문구
자체가 아예 빠진 경우였다는 사실이 이를 뒷받침한다. citation=True 92.6%라는
수치는 "형식을 갖췄는가"에 가깝고 "인용이 실제로 정확한가"의 보증은 약하다.
**미수정** — 검증 로직을 report_id/chunk_id 실제 일치로 강화하는 게 다음
후보(§12).

## 5. 결론 — 이 시스템은 38개사/6개 route에 얼마나 잘 일반화하는가

**정직하게 말하면: 부분적으로 잘 되지만, 자동 지표가 보여주는 것보다는
약하다.**

- **잘 되는 부분**: 명확한 단일 수치 조회(단일 회사, 존재하는 지표)는 강하다
  — 삼성전자/한미반도체/하이브 등 원문대조 전부 정확히 일치했다. 부채비율
  같은 파생 계산도 정확하다. 정정 이력(get_correction_history)도 로직
  자체는 정확하다(단 validator 인식에 버그가 있었을 뿐 — 이제 수정됨).
  존재하지 않는 데이터에 대해 할루시네이션 대신 "확인할 수 없음"이라고
  답하는 원칙은 대체로 잘 지켜진다(신한지주/크래프톤 사례).
- **약한 부분**:
  1. **"확인할 수 없음"이 항상 정직한 실패는 아니다** — §4-D에서 11건이
     실제로는 존재하는 데이터를 못 찾은 검색 실패였다. 이건 grounded/
     citation 자동 지표를 100% 신뢰하면 절대 못 잡는다(오히려 "안전하게
     거짓말 안 함"으로 보상받는 방향으로 실패한다). 100문항 중 최소
     11건(11%)이 이 유형이었다.
  2. 답변 생성이 여전히 가끔 인용 형식을 빠뜨린다(7건, 7%) — 내용은
     맞는데 검증을 통과 못 하는 애매한 실패.
  3. 표/재무제표 단위 변환에서 여전히 10배 오류가 재현된다(레인보우로보틱스,
     알테오젠 계열과 같은 패턴) — 회사가 바뀌어도 이 취약점은 없어지지 않았다.
  4. validator 자체의 신뢰도가 이번에 재검증됐다 — 오탐(§3-A, 12건 수정)과
     미탐(§3-B, 알테오젠, 1건 이상 가능성) 둘 다 실측으로 확인됐다.
- **API 안정성**: 5%가 수십분 hang 후 완전 실패했다 — 실사용 환경이라면
  타임아웃을 훨씬 짧게(예: 60~120초) 잡고 재시도/폴백 전략이 필요하다는
  뜻이다. 지금처럼 45~97분 동안 아무 응답 없이 매달리는 건 production
  관점에서 용납하기 어렵다.

**요약하면**: 코어 검색·계산·정정분석 로직은 38개사 전반에 잘 일반화된다.
하지만 (a) "최근 데이터"를 다루는 검색의 breadth/relevance, (b) 답변의
인용 형식 준수, (c) 표 안 숫자의 단위 변환 정확도, (d) validator 자체의
완전성 — 네 가지는 회사 수를 늘려도 저절로 해결되지 않는, 여전히 남아있는
근본적 한계다.
