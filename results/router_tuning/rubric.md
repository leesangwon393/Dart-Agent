# Router 분류 기준 (Rubric) — 파인튜닝 학습데이터용

Stage 9에서 확정한 6개 route(`hcx_structured_router`, `results/router/`)를
CLOVA Studio 분류 튜닝 학습데이터로 확장하면서, 파일럿 생성(150개) 검토 중
실제로 애매했던 경계 케이스 2건을 사용자와 함께 확정했다.

## 확정된 경계 규칙

1. **"기간별 비율/지표 비교"** (예: "3개년 자본잠식 비율을 비교해줘",
   "최근 3년간 배당수익률을 비교해볼까 해") → **multi_compare**
   (calculation 아님 — 순수 산출 요청이 아니라 "여러 기간을 나란히 놓고
   본다"는 비교 의도가 핵심이라고 판단)
2. **"두 회사의 정정이력 비교"** (예: "A사와 B사 사이의 정정공시 비교
   분석 가능합니까?") → **correction_analysis**
   (multi_compare 아님 — 비교 대상이 있어도 질문의 핵심 관심사가 "정정"
   이라는 주제 자체이므로 correction_analysis 로 분류)

## 카테고리 설명 (생성/라벨링 시 사용, `generate_route_pilot.py` CATEGORY_DESC 와 동기화)

| route | 설명 |
|---|---|
| single_lookup | 특정 회사의 단일 사실/수치 조회. 비교·계산·지분·이벤트가 아닌 순수 사실 하나(매출액, 대표이사, 설립일, 업종 등) |
| correction_analysis | 정정공시(기재정정)의 사유/변경내용/전후비교/이력. **두 회사 간 정정이력 비교도 포함**(위 규칙 2) |
| multi_compare | 두 회사 간 비교, 또는 한 회사의 여러 기간(연도/분기) 간 비교. **기간별 비율/지표 비교도 포함**(위 규칙 1) |
| calculation | 증가율/CAGR/비율/증감액 등 **단일 시점 또는 단일 기간 쌍**에 대한 산술 계산 요청 (여러 기간을 나열/비교하는 게 아니라 "계산해줘"가 핵심) |
| ownership_analysis | 최대주주/지분율/주요주주/지분변동/자기주식. "최대주주가 누구야?"처럼 단순 사실처럼 보여도 최대주주/지분 관련이면 여기로(single_lookup 아님) |
| event_analysis | 유상증자/계약체결/인수합병/시설투자/자사주 취득 등 이벤트 발생 여부/내용. **개수를 세는 질문("몇 건이야?")도 포함** — Stage 이후 발견된 취약점이라 의도적으로 커버 |

## 파일럿 생성 결과 (v1, 검토완료)

`pilot_v1_raw.json`: HCX 생성 원본(150개 목표, 141개 생성).
`pilot_v1_reviewed.json`: 위 규칙 적용 + 오분류 수정 후 최종본(149개).

| route | 개수 |
|---|---|
| single_lookup | 24 |
| correction_analysis | 25 |
| multi_compare | 26 |
| calculation | 21 |
| ownership_analysis | 27 |
| event_analysis | 26 |
| **합계** | **149** |

### 발견/수정한 오분류 (3건)
- "[COMPANY_1]와 [COMPANY_2], 두 회사의 시가총액을 비교해봐" — calculation
  으로 생성됐으나 순수 비교 질문 → multi_compare 로 이동.
- "[COMPANY]의 최근 주요 주주 변동사항이 있나요?" — single_lookup 으로
  생성됐으나 지분 관련 → ownership_analysis 로 이동.
- "[COMPANY]의 최대주주는 누구야?" — single_lookup 으로 생성됐으나 최대주주
  관련은 전부 ownership_analysis 로 통일 → 이동.
- "[COMPANY]의 최근 공시는 무엇인가요?" — single_lookup 으로 생성됐으나
  포괄적 이벤트 질문 → event_analysis 로 이동.

### 관찰
- 명시적으로 유도한 카운팅형(event_analysis "몇 건이야?") edge case가
  실제로 잘 생성됐다 — 어제 발견한 취약점을 학습데이터에 반영하는 전략이
  유효함을 확인.
- 정확히 중복된 문장은 0건, 어투(반말/존댓말/명령문)도 다양하게 나옴.
- ~2~3%(149건 중 3~5건) 비율로 경계 케이스/오분류가 자연 발생 — 대량
  생성(1,200건) 전에 반드시 사람 검토를 거쳐야 함을 재확인.

## CLOVA Studio 요구사항 대비 현재 상태
- 카테고리당 최소 200행 필요(공식 문서) — 현재 21~27행/카테고리, **약 12%
  수준**. 전체 1,200행까지 확대하려면 이번 파일럿과 같은 생성→검토
  사이클을 카테고리당 8배 반복해야 한다.
- 라벨 형식(띄어쓰기·특수문자 금지) 확인 필요 — 현재 route 이름
  (`single_lookup` 등 언더스코어 포함)이 그대로 통과되는지 실제 콘솔에서
  검증 안 됨. 필요시 한글 단어(단순조회/정정분석/다중비교/계산/지분분석/
  이벤트분석)로 치환 고려.
